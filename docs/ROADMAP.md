# 路线图

## 定位与参照

功能覆盖向 [chinese-poetry/chinese-poetry](https://github.com/chinese-poetry/chinese-poetry)
看齐(多品类古典诗文),数据策略相反:该上游聚合多来源、体量大但质量不齐;本仓库
坚持**小而可信、增量扩展**——每个 collection 绑定一个固定来源,宁可品类少而经得起
核对,不追体量。

## 原则

1. 已有基线不推倒重来:证据分级、可重现导入、发布/回滚体系继续沿用。
2. 扩库以 collection 为单位:一个 collection = 一个固定版本来源 = 一次导入 +
   一份报告;不零散添加单篇作品。
3. 证据等级不冒充:电子文本来源不得标为扫描核验;机械校验不得描述为人工校勘。
4. 未核验的信息宁可缺位(如 `position` 为 `pending`),不填估计值。

## 基线(已完成)

- 50 首唐诗(`primary-scan-reviewed`)+ 276 首宋词(`digital-text-checked`),共 326 首。
- 版本化随机 API、启动全量校验、uv 锁定的导入管线、CI、标签发布与受控部署。

## P0:API 消费侧地基(纯代码,无数据依赖)

1. 新增 `GET /api/v1/works/{id}`:按稳定 ID 返回单篇,使作品可被引用和缓存。
2. 随机响应附带出处摘要(`evidence.level` 与来源版本信息),让消费者能直接展示
   "据何版本核校",把可信来源的价值送达使用方。

## P1:唐诗主选本收尾(第一个 complete 的 collection)

49 首的目录位置核验(`position: pending` → 确认值),依据已保存的春明书店本
见证逐首定序;完成后 `tangshi-sanbaishou-1933` 可标 `complete`,API 返回书内
序号。该任务同时验证"导入 → 核验 → complete"的增量闭环。

## P2:品类扩展(顺序为候选,以实际选定的来源为准)

沿宋词已趟出的流程逐个品类推进,候选顺序:

1. 诗经(篇目固定、文本稳定,适合作为下一批电子文本导入)
2. 楚辞
3. 元曲(曲牌与分片结构需先扩展模型,前置一个设计评估)
4. 其余视需求评估:古诗十九首、乐府、论语等散文类是否纳入另行决策(体裁
   模型目前面向韵文)

每个品类立项时须先回答:固定来源是哪个提交/哪个本子、预期证据等级、隔离规则。

## 非目标

- 与上游的体量竞争(全唐诗五万首级别的收录不在当前目标内)。
- 全量宋词扫描核验:保持 `digital-text-checked`,仅对具体疑点个案核对。
- 数据库、后台管理界面、自建 OCR 管线。
